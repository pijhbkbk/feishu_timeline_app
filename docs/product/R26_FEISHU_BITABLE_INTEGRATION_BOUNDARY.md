## 为什么本轮不直接嵌入并双向写入

当前系统的项目、流程、任务、评审、材料和审计由 PostgreSQL 与后端状态机共同裁决。
若把多维表格直接变成第二个可写主数据源，会产生以下风险：

- 表格编辑可能绕过流程状态、材料门禁、权限和幂等校验；
- 飞书记录与系统任务之间需要稳定的一对一 ID 映射；
- 双向并发编辑需要冲突策略、重放与失败补偿；
- 删除、字段类型变化和人员字段失效会影响在途项目；
- 表格审计不能替代系统业务审计。

因此，本轮采用原生可编辑分工表，并复用现有后端分配服务和审计链路。

## 可选的后续接入方案

推荐按以下顺序独立立项：

1. **只读引用**：后台提供“打开飞书多维表格”入口，不做数据同步；
2. **单向导入预览**：读取指定表/视图，先做字段映射、差异预览和逐行校验，不立即
   写业务数据；
3. **受控同步**：只有通过预览的变更才能调用系统 command 接口，由服务端逐条裁决；
4. **回写结果**：仅回写系统生成的状态摘要和系统记录 ID，不允许飞书字段直接决定
   下一节点；
5. **冲突治理**：使用记录版本、同步游标、幂等键、失败队列和审计日志。

真正接入前必须由产品负责人确认：

- 飞书应用和租户；
- 目标 app/table/view；
- 字段映射与数据归属；
- 只读、单向还是双向；
- 所需开放平台权限及管理员审批；
- 历史数据迁移与回滚方案。

未经上述确认，不申请持久权限、不创建 webhook、不写入该多维表格。
