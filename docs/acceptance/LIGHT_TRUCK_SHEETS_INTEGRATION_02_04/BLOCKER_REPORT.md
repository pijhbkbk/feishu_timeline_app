新定位原因：业务 `runtime.ts` 将交互ready绑定到`LifecycleStages.Steady`。安装的Univer 1.0.4在首次`Rendered`后固定等待`STEADY_TIMEOUT = 3e3`才进入Steady，业务加载遮罩也随之等待。最新engineReady为4583.35/3995.38 ms；随后滚入可见区域又用364.25/537.12 ms。10批图片元数据读取确实串行，但当前读数层不等待该请求完成，不能把它直接认定为此门禁根因或从总耗时扣除。

下一方案：只将本系统交互ready绑定到已完成首次渲染、编辑/剪贴板/绘图与权限控制器已注册的`Rendered`；不修改第三方固定计时、不手动推进生命周期、不停用图片、自动保存或权限。保留原来的延后菜单初始化。先对真实runtime边界补Rendered前后/处置回归及独立源码审查，再生成新不可变候选，在相同URL、数据规模和计时口径重新验证。这是基于新原因的修复验证，不重跑同一失败候选碰碰运气。

不需要新的产品决定：仍在已授权可逆开发与隔离验证范围。真实系统IME因电脑控制工具两次策略加载失败仍为NOT_VERIFIED；其他工作继续。最终结果须在PERFORMANCE.md和UI_ACCEPTANCE.md分别说明，失败优先于未验证，不将本报告抹除或改成历史PASS。
